# From Brief to Verified Artifact

Use this when the user requests substantial construction or redesign. Keep the working specification in existing task context unless a persistent record benefits delivery. A small repair needs only its affected decision and verification.

## Establish decisions that constrain implementation

Write a compact contract using the actual brief:

| Field | Concrete content |
| --- | --- |
| User task | What the user must understand or accomplish; required path to completion |
| Identity | Product-specific organizing idea, supplied brand constraints, expressive and quiet regions |
| Evidence | Assets and references actually inspected; known facts, assumptions, and unavailable material |
| Composition | Primary subject, reading order, shared rails, useful comparisons, type and color roles |
| State | Selected identity, configuration, pending/failed/successful outcomes, source of truth |
| Space | Units, axes, important dimensions, parent/pivot/attachment ownership where relevant |
| Motion | Trigger, owner, path, timing or progress, interruption, endpoint, reduced-motion equivalent |
| Delivery | Required views, content extremes, input conditions, rendering capabilities, performance conditions |
| Acceptance | Observable outcome and the inspection or assertion that can establish it |

For example, a hinge inspection tool needs an identifiable hinge, visible axis, a bounded angle control, and an exact neutral return. The state is the selected angle; the model and DOM control must agree. A cinematic opening is optional unless it helps the requested explanation. A marketing product page may instead concentrate expression in a framed object and editorial title while keeping purchasing decisions direct.

## Resolve uncertainty with a representative slice

Build the most informative small portion early: the real title beside the actual product, a material under its intended light, a hinge at both extremes, or a selection change during a pending request. Use the slice to decide architecture and visual relationships before expanding the same uncertainty across the whole artifact.

Compare genuinely different directions only where identity is unresolved. Choose based on product fit, legibility, distinctive character, asset feasibility, and cost. Keep the chosen direction through later sections and error/loading states. Do not turn exploratory variants into a mandatory ceremony for every task.

## Convert choices into values and ownership

Implementation needs actual decisions: a loaded font and role scale; palette values in context; dimensions and frames; state transitions; motion values and bounds. Use examples as starting points, then adapt to content, scene units, and observed response. Keep canonical object configuration separate from its exploded pose or camera view.

Use one source for facts that must agree. A selected finish updates its label, swatch, material, and any accurate product details together. A new dimension updates the dependent attachment frame and movement bounds. If upstream choices change, revisit their downstream dependencies.

## Make acceptance decisions from evidence

Judge the complete requested journey. Inspect the ordinary states as carefully as the opening. A useful record is: condition, observed failure, responsible decision, correction, matched recheck. Keep it concise and tied to the artifact.

Approve a result for the conditions actually observed when its primary task works, structural relationships hold, identity is coherent, relevant access paths work, and material visual defects are resolved. A successful build verifies construction. Screenshots support static appearance; playback supports timing; behavior checks support state invariants. Use each for its own question.

Stop additional polish when the acceptance conditions are supported and no consequential defect remains in scope. Reopen a decision when new evidence shows a failure. Avoid endless self-scoring and speculative features. A remaining unavailable observation belongs in the handoff with the exact limitation.

## Handoff

Deliver the runnable artifact or requested files, use/run instructions, changes that matter, verification conditions and results, and consequential unresolved limits. Preserve editable structure when future revision is part of the deliverable. Treat design awards and model-equivalence claims as unverified unless independently established; the package transfers methods and evidence, with results dependent on the host and model.
